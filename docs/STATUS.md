## Current product boundary

Schuss currently has:

- a function-first catalog with provenance and availability facets;
- one authoritative, client-neutral DSP graph model shared by CLI, desktop,
  and AI adapters;
- deterministic project/workspace authoring and build planning;
- the existing Ksoloti legacy backend and direct compiler path;
- a bounded JUCE-independent native desktop runtime for the seven accepted
  Task 031/032 factory types;
- deterministic offline rendering and a headless JUCE audio/MIDI session
  adapter;
- a six-entry Instrument Lab audition library with bounded local JUCE process
  launch and an Instruments-first desktop surface; Pamplist alone has canonical
  musical identity, while all launch authority remains prototype-bound;
- private, uninstalled arm64 VST3 target builds for Tide Pit and Pamplist,
  each with an exact internal 48 kHz Core and bounded adapters for 32, 44.1,
  48, 88.2, 96, 176.4, and 192 kHz, with offline host evidence only;
- a noncanonical Layerwell 0.2 meta-instrument with complete accepted Tide Pit
  and Pamplist panels, deterministic three-layer/trim Core evidence, and an
  authenticated but unlaunched JUCE standalone build;
- a noncanonical Wanderbody 0.1 recent-memory standalone prototype with
  deterministic Hover/Drunk, tuple-recurrence, fragment, modal-body, and
  unlaunched authenticated arm64 target-build evidence;
- device-independent performance-control contracts and Gills/MIDI
  configurations; and
- source-neutral object collections and explicit implementation providers.

The seven native factory types remain a bounded proven runtime cohort, not a
permanent palette ceiling. The complete DSP graph remains accessible, and any
future controller execution layer must continue to reference public instrument
facets rather than DSP node IDs.
